# resilience4cata 1.0.0-RC4: your own bulkhead no longer opens the breaker

The fourth release candidate for 1.0.0 is on Maven Central. The API is the same as in RC3, and one behaviour changes: the circuit breaker no longer counts the rejections of the method's own bulkhead, rate limiter or adaptive limit as failures.

*14 November 2026 · by [fabiangftech](https://github.com/fabiangftech), author of resilience4cata*

## What the pilot found

Nobody runs resilience4cata in production yet, so before 1.0 there is a [pilot](https://github.com/fabiangftech/resilience4cata/tree/main/pilot), the closest thing to one without a user. It runs three small services, one each on Spring Boot, Micronaut and Quarkus. Each takes resilience4cata from Maven Central, as its guide says, and calls a simulated backend over HTTP. k6 sends them 10 minutes of load: 1500 orders per second, with the backend down for one minute and slow for another. The method that calls the backend uses the usual stack:

<!-- not-compiled: the pilot's service, abridged -->
```java
@Fallback(method = "lastKnown")
@Retry(name = "inventory", maxAttempts = 3, delay = "20ms")
@CircuitBreaker(name = "inventory", windowSize = 100, minimumCalls = 20, failureRateThreshold = 50,
        waitInOpen = "5s", halfOpenCalls = 5)
@Timeout("200ms")
@Bulkhead(name = "inventory", maxConcurrent = 40, maxWait = "20ms")
public String stock(String id) throws IOException, InterruptedException { ... }
```

On 1.0.0-RC3, the Spring service opened its breaker during its cold start, and the backend had not failed once. Calls are slower while a JVM warms up, so 40 of them filled the bulkhead and the next ones were rejected with `BulkheadFullException`. The breaker sits outside the bulkhead in the default order, so it saw those rejections as failures. Once its window held 20 calls and half of them were rejections, it opened, and orders went to the fallback while it stayed open.

The first run of the pilot avoided it with `ignoreOn = BulkheadFullException.class` on the breaker. A user would have to know that line was needed, and nothing in the error would tell them.

## Why it is a trap

The breaker answers one question: is the dependency failing? A full bulkhead, an exhausted rate limiter or a full adaptive limit answer a different one: is this application busy? Mixing the two has three bad effects:

- A burst of your own traffic opens the breaker while the dependency is healthy, and the fallback answers calls that would have succeeded a moment later.
- An open breaker then rejects even the calls the bulkhead would have let in, so overload turns into an outage that lasts at least `waitInOpen`.
- A half-open probe rejected by the bulkhead counts as a failed probe, so the breaker opens again without asking the dependency anything.

Resilience4j has the same trap: its bulkhead and rate limiter sit inside the breaker too, and its `BulkheadFullException` and `RequestNotPermitted` count as failures unless you list them in `ignoreExceptions`. The difference in 1.0.0-RC4 is that you no longer have to remember.

## The rule in RC4

The circuit breaker never records `BulkheadFullException`, `RateLimitExceededException` or `AdaptiveLimitFullException`. They count neither as failures nor as successes, and a half-open probe that gets one gives its permit back. That holds whatever `recordOn`, `ignoreOn` or a classifier say, for synchronous, `CompletionStage`, `Mono` and `Flux` methods and for the `Pipeline`. Details are on the [circuit breaker page](../policies/circuit-breaker.md#with-other-policies).

Two exceptions still count, because they do say something about the dependency:

- `CallTimeoutException`: a dependency that is too slow is failing. A slow dependency therefore still opens the breaker, through its timeouts and slow calls.
- `CallNotPermittedException` from another breaker further in: the dependency behind it is failing.

The rule is fixed and has no switch, on purpose: no one should have to configure their way out of a trap. A breaker that should react to overload is a different tool, and that is what the [bulkhead](../policies/bulkhead.md) and the [adaptive limit](../policies/adaptive-limit.md) are for.

## What changes for you

- If you added `ignoreOn = BulkheadFullException.class`, or the rate limiter's or adaptive limit's rejection, to a breaker, you can remove it. Leaving it in does no harm.
- If you migrate from Resilience4j, drop those entries from `ignoreExceptions`: the [migration guide](../migrate/from-resilience4j.md#local-rejections) has the note.
- Nothing else changes. Every published module was compared with RC3: no incompatible change in the API. The tests of `examples`, compiled with RC3's processor, pass on RC4's modules, so code generated by RC3 keeps working.

## The pilot again

The pilot then ran on the new code with no `ignoreOn`, on the same machine.

> [!MEASURED]
> AWS `c7g.4xlarge` (Graviton3), JDK 25, 2026-11-13, the code of 1.0.0-RC4. Each service had 4 cores, the backend 4 and k6 8. Spring Boot's row; Micronaut and Quarkus are within a millisecond of it up to p99. Run `20261113-202658` of `pilot/run.sh aws`, summarized in the [pilot's README](https://github.com/fabiangftech/resilience4cata/tree/main/pilot).

| Phase | Orders answered by the backend | p50 | p99 | p99.9 |
|---|---|---:|---:|---:|
| steady | 100 % (its 1 % of 503s retried away) | 6.8 ms | 28.7 ms | 42.3 ms |
| backend down | 0 %: the breaker answered every order | 0.1 ms | 0.2 ms | 1.2 ms |
| backend slow (1 s) | 0 %: breaker, bulkhead or timeout; nobody waited the second | 0.1 ms | 0.3 ms | 260.6 ms |
| after the outages | 100 % | 6.8 ms | 28.7 ms | 42.1 ms |

All three services passed every check, about 1.04 million requests each. In the Spring service, one order out of the 270,000 of the steady phase was answered by an open breaker. It started just before the backend went down at minute 4, and its retries found the breaker already open: the breaker doing its job, not the old trap.

```groovy
dependencies {
    implementation 'dev.resilience4cata:resilience4cata-all:1.0.0-RC4'
    annotationProcessor 'dev.resilience4cata:resilience4cata-processor:1.0.0-RC4'
}
```

#### **Gradle (Kotlin)**

<!-- not-compiled: build configuration -->
```kotlin
dependencies {
    implementation("dev.resilience4cata:resilience4cata-all:1.0.0-RC4")
```

<!-- not-compiled: build configuration -->
```xml
<dependency>
  <groupId>dev.resilience4cata</groupId>
```

## What comes next

If nothing else needs to change, 1.0.0 follows with the same API and the [compatibility](../reference/compatibility.md) promise starts. This change is the kind a release candidate is for: after 1.0, changing what the breaker counts would have surprised users in a minor version. If you try RC4 and something surprises you, open an [issue](https://github.com/fabiangftech/resilience4cata/issues) or a [discussion](https://github.com/fabiangftech/resilience4cata/discussions) on GitHub.
