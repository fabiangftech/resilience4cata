# Registro de cambios

Cambios notables en cada versión de resilience4cata, de la más reciente a la más antigua.

El formato sigue [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/), y el proyecto usa [Versionado Semántico](https://semver.org/lang/es/spec/v2.0.0.html). Hasta 1.0.0, una versión menor puede cambiar la API.

## [0.12.0] - 2026-10-31 :id=0.12.0

La revisión de la API antes de 1.0: esta versión cambia la API en muchos puntos, así que lee **Cambiado** antes de actualizar. El código generado por 0.11.0 o antes se debe compilar de nuevo con este procesador.

### Cambiado

- **El código generado y core siguen una sola regla de compatibilidad.** El código generado por el procesador `1.a` funciona sobre core (y reactor) `1.b` para todo `b >= a`, dentro de una versión mayor, así que una librería compilada con resilience4cata sigue funcionando cuando una aplicación lo actualiza. Cada constructor generado comprueba primero que el runtime sea lo bastante nuevo y, si no lo es, falla enseguida con el error nuevo [R4C-RT-021](errors.md#r4c-rt-021), en vez de con un `NoSuchMethodError` en la primera falla en producción. El código generado por 0.11.0 o antes se debe compilar de nuevo con este procesador.
- Las fábricas de políticas que llama el código generado (`ResilienceRegistry.retryPolicy(...)`, `circuitBreakerPolicy(...)` y las demás, 16 métodos) ya no son métodos públicos de `ResilienceRegistry`: el código generado llama a `dev.resilience4cata.generated.Policies`, que es solo para código generado. Para políticas construidas en código, usa `Pipeline`.
- **Los siete tipos `*Config` (`RetryConfig`, `CircuitBreakerConfig`, …) son clases final en vez de records**, que se construyen solo con `builder()` y `toBuilder()`, así que se pueden agregar atributos en versiones menores sin dejar constructores viejos. Los accessors (`config.maxAttempts()`), `equals`, `hashCode` y `toString` no cambian; desaparecen los constructores públicos y los record patterns (`case RetryConfig(var …)`), y también el constructor de `RetryConfig` de 0.2.0. Comparten la interfaz sellada nueva `PolicyConfig`, que ahora devuelve `LockedOverride.config()` en vez de `Record`.
- **`ResilienceSnapshot` es una clase final en vez de un record** y solo la crea el registry: un tipo de política agregado más adelante es una lista más, no un constructor nuevo. Sus accessors no cambian; desaparecen los constructores de 0.3.0 a 0.11.0. Nuevo: `only(id)` (las instancias de un id), `isEmpty()` y `toMap()`, el snapshot como mapas y listas simples, con una forma documentada ([Snapshots](guides/observability.md#snapshots)). Desaparece el constructor de `RetrySnapshot` de 0.2.0.
- El endpoint de actuator de Spring Boot y el endpoint de management de Micronaut sirven los dos `ResilienceSnapshot.toMap()`, así que su JSON es el mismo. En Spring Boot, las duraciones ahora son strings ISO-8601 y las tasas no finitas, `null`, como ya las escribía Micronaut; las operaciones de `ResilienceEndpoint` devuelven un `Map`.
- **Un solo nombre para el id de una instancia: `id()`.** Los snapshots (`CircuitBreakerSnapshot.instance()` y los demás), los eventos (`ResilienceEvent.instance()`), las excepciones y `FallbackContext` (`instanceId()`) y `LockedOverride` ahora usan todos `id()`, como los handles y `Pipeline`. En el JSON de los endpoints, la clave `instance` ahora es `id`. (Las etiquetas de las métricas no cambian aquí.)
- `AdaptiveLimitHandle.inFlight()` y `AdaptiveLimitSnapshot.inFlight` ahora se llaman `concurrentCalls`, como en el bulkhead y en la métrica `r4c.adaptivelimit.concurrent.calls`.
- `AdaptiveLimitEvent.LimitChanged.windowLatencyNanos` (un `long`) ahora es `windowLatency`, un `Duration` como todas las demás duraciones de los eventos.
- `LimitExceededException` se renombra a `AdaptiveLimitFullException`, que ya no se confunde con el `RateLimitExceededException` del rate limiter.
- Los cuatro rechazos (`CallNotPermittedException`, `BulkheadFullException`, `RateLimitExceededException`, `AdaptiveLimitFullException`) extienden la nueva `CallRejectedException`, así que un solo `catch` los maneja todos.
- **La etiqueta `instance` de las métricas ahora es `name`**, en `resilience4cata-micrometer` y en `resilience4cata-opentelemetry`. Prometheus agrega su propio label `instance` (host:puerto del target) a cada serie que recolecta y renombraba el nuestro a `exported_instance`; los dashboards y alertas que filtran por `instance` deben usar `name`. Los nombres siguen con puntos (el estilo de Micrometer) y las tasas del breaker siguen en porcentaje, ahora documentado como fijo ([Nombres de métricas](guides/observability.md#metric-names)).
- `OpenTelemetryMetrics.bindTo` se comporta como `MicrometerMetrics.bindTo`: vincular otra vez el mismo registry no hace nada (antes reportaba cada gauge dos veces), y tampoco vincular después de `close()` (antes lanzaba `IllegalStateException`).
- `PipelineOperator` (para `Mono`) se renombra a `MonoPipelineOperator`, junto a `FluxPipelineOperator`.
- **Los perfiles ya no ganan a fuentes más fuertes.** Una clave bajo un perfil activo sigue ganando sobre la misma clave sin perfil en la misma fuente, pero una variable de entorno o una propiedad del sistema ahora gana sobre una clave de perfil en un archivo, como en Spring Boot y Quarkus: la variable `R4C_…` de un operador ya no se ignora cuando un perfil pone la misma clave.
- Spring Boot: la API Java es el paquete `dev.resilience4cata.spring` (`ResilienceRegistryCustomizer`, `ResilienceHealthIndicator`, `ResilienceEndpoint`). `ResilienceSpringProperties` se movió a `dev.resilience4cata.spring.autoconfigure`, y los métodos `@Bean` de las clases de auto-configuración ya no son públicos: ahí el contrato son los nombres de las clases de auto-configuración (para `exclude`), los nombres de los beans y los nombres de las propiedades `resilience4cata.spring.*`, que no cambian.
- **`enabled` en las anotaciones de políticas es un `boolean`** (`@Retry(enabled = false)`) en vez de los strings `""`, `"true"` y `"false"`; no escribirlo sigue heredando. [R4C-ATR-006](errors.md#r4c-atr-006), el error para cualquier otro string, queda retirado: ahora el compilador revisa el valor.
- Los miembros que son públicos solo para otro módulo de resilience4cata (el uso que hace el registry de los constructores y configs de las políticas, `PolicyEnvironment`, el despacho de eventos, el soporte de streams de `Pipeline` para el módulo reactor, el `AnnotatedClassesFilter` de Micronaut) llevan `@Internal`, y el chequeo de compatibilidad de API deja fuera lo marcado `@Internal` o `@Experimental`. Los constructores de políticas que solo usaban los tests ya no son públicos.

### Corregido

- Spring Boot: las claves que empiezan con `r4c.` (el prefijo corto que documenta la referencia de configuración, y que leen Micronaut y Quarkus) se ignoraban en silencio; ahora se leen como las claves `resilience4cata.`. `r4c.spring.*` se salta, como `resilience4cata.spring.*`.
- La descripción de `r4c.hedge.failed` es "Calls through a hedge that failed": cuenta cada llamada fallida a través de un hedge, se haya lanzado un hedge o no.

## [0.11.0] - 2026-10-30 :id=0.11.0

### Agregado

- **`resilience4cata-reactor`: el `Mono` de Project Reactor.** Un método anotado que devuelve `Mono<T>` (o `Mono<? extends T>`, `Mono<?>`) recibe cada política en su forma asíncrona, hedges incluidos: nada corre antes de una suscripción, cada suscripción es una llamada, cada intento vuelve a llamar al método, el `Context` del suscriptor llega a cada intento y al fallback, y cancelar la suscripción cancela la llamada a través de cada política (el breaker no registra nada, el bulkhead y el adaptive limit liberan su slot). Los fallbacks pueden devolver el valor o un `Mono` de él. El `Mono` generado pasa el TCK de Reactive Streams, y ninguna política bloquea un hilo de Reactor (verificado con BlockHound). Para código que no puedes anotar, `PipelineOperator.of(pipeline)` aplica un `Pipeline` con `Mono.transform`. Reactor 3.6 o posterior. Un método `Mono` compilado sin el módulo es el nuevo error [R4C-ASY-003](errors.md#r4c-asy-003). En el BOM. Consulta [Project Reactor](guides/reactor.md).
- **`resilience4cata-reactor`: el `Flux` de Reactor.** Un método anotado que devuelve `Flux<T>` recibe las políticas adaptadas a un stream: cada intento se vuelve a suscribir al `Flux` del método y sus elementos van al suscriptor a medida que llegan, con su demanda y su contexto. El primer elemento compromete la llamada: el retry y el fallback solo actúan antes de él, y un fallo posterior llega tal cual al suscriptor. `@Timeout` se reinicia con cada elemento (hasta el primero, entre dos, hasta el final), sin un timer por elemento; las llamadas lentas del circuit breaker y las muestras del adaptive limit son el tiempo hasta el primer elemento; el bulkhead ocupa su lugar durante todo el stream; el rate limiter toma un permiso por intento. Los fallbacks devuelven un `Flux` o un valor. `@Hedge`, los classifiers y un `@PolicyOrder` que cambie el orden son el nuevo error [R4C-ASY-004](errors.md#r4c-asy-004) en un método `Flux`. El `Flux` generado pasa todas las reglas del TCK de Reactive Streams. Para código que no puedes anotar, `FluxPipelineOperator.of(pipeline)` (un pipeline con hedge o classifier es el nuevo error [R4C-RT-020](errors.md#r4c-rt-020)). Consulta [Project Reactor](guides/reactor.md#flux).
- El circuit breaker, el bulkhead, el rate limiter y el adaptive limit registran al momento un stage que ya está completo cuando la llamada vuelve, sin enlace ni callback, como ya hacía el timeout: menos bytes y nanosegundos por llamada en los métodos async cuyo resultado ya está.
- Los chequeos de Spring Boot, Micronaut y Quarkus de un método con retry o hedge dentro de una transacción ([R4C-SPR-004](errors.md#r4c-spr-004), [R4C-MN-005](errors.md#r4c-mn-005), [R4C-QK-002](errors.md#r4c-qk-002)) también ven los métodos `Mono`, cuyas capas de retry y hedge están en una lambda del código generado.
- Las imágenes nativas se construyen y prueban ahora en la CI: la aplicación de la guía de Quarkus, como imagen nativa de GraalVM (GraalVM para JDK 25), sirve su clase anotada, los envoltorios de interfaz y de cliente REST, la comprobación de disponibilidad y las métricas, y métodos `Mono` y `Flux` de una clase anotada y de una interfaz envuelta, sin configuración nativa adicional. Ver [Quarkus](guides/quarkus.md#native).

### Cambiado

- [R4C-ASY-002](errors.md#r4c-asy-002) ya no cubre el `Mono` ni el `Flux` de Reactor, y su mensaje los sugiere con `resilience4cata-reactor`.

### Corregido

- **El trabajo que la librería ejecuta más tarde ya no hereda el contexto de hilo de otro request, ni un class loader viejo después de una recarga.** Los hilos de timer de la librería se inician una vez por JVM, y heredaban el context class loader y los valores `InheritableThreadLocal` del request que los iniciaba; los virtual threads que lanzan (el siguiente intento de un retry, un hedge, un timeout async que vence) los heredaban a su vez, y una llamada en cola de un bulkhead heredaba los de la llamada que liberó su lugar. Así, después de una recarga en caliente (dev mode de Quarkus, Spring DevTools) los intentos posteriores corrían con el class loader de la aplicación vieja, que además quedaba en memoria, y con un security context o un MDC heredables un intento podía correr con los valores de otro request. Los hilos de timer ahora tienen el class loader de la librería y no heredan nada; el trabajo corre con el context class loader del hilo que hizo la llamada y sin valores heredados.
- **El rate limiter asíncrono ya no estaciona el hilo que llama.** Tras perder la carrera por un permiso se estacionaba 1 ns antes de reintentar, algo que un hilo de event loop (Netty, Reactor) nunca debe hacer; ahora reintenta de inmediato. Con mucha contención sobre un mismo limiter esto cuesta más por llamada ([benchmarks](benchmarks.md)). El rate limiter síncrono no cambia.
- **Spring Boot: un bean del que depende un post-procesador de la aplicación ya no pierde sus políticas en silencio.** Spring crea ese bean antes de registrar el post-procesador de resilience4cata, así que un bean que implementaba una interfaz anotada nunca se envolvía. Ahora el arranque se detiene con el nuevo error [R4C-SPR-005](errors.md#r4c-spr-005), que nombra el post-procesador e indica inyectar el bean de forma diferida (`ObjectProvider` o `@Lazy`).
- **Micronaut: un método `@EventListener` de una clase anotada recibe cada evento una sola vez.** Micronaut genera un bean adaptador por método listener, para la clase y para su subclase generada; los dos llamaban al bean de la subclase, así que cada evento se procesaba dos veces. Ahora los adaptadores de la clase se descartan junto con la clase.

## [0.10.0] - 2026-10-27 :id=0.10.0

### Agregado

- **`@PolicyOrder`: cambia el orden de las políticas de un método.** Nombra capas (`Layer.RETRY`, `TIMEOUT`, `CIRCUIT_BREAKER`, …) que se mueven juntas, en el orden indicado, al lugar de la más exterior de ellas; las demás conservan su orden por defecto. `@PolicyOrder({TIMEOUT, RETRY})` pone un único timeout alrededor de todo el bucle del retry, `{CIRCUIT_BREAKER, RETRY}` registra un resultado por operación en el breaker, `{BULKHEAD, RETRY}` mantiene el slot entre reintentos. En un método, un tipo o un bundle; se decide al compilar, y el fallback sigue siendo la capa más exterior. Nombrar una capa dos veces es [R4C-ORD-001](errors.md#r4c-ord-001). Sin ella, o cuando no cambia nada, el código generado no cambia. Un `Pipeline` mantiene el orden por defecto. Consulta [Cambiar el orden](policies/README.md#changing-the-order).

## [0.9.0] - 2026-10-27 :id=0.9.0

### Cambiado

- **Los tipos de retorno reactivos son un error de compilación.** Un método con anotaciones de resiliencia que devuelve un tipo reactivo perezoso (`Flow.Publisher` o el `Publisher` de Reactive Streams, es decir `Mono` y `Flux` de Reactor; `Uni` y `Multi` de Mutiny; los tipos de RxJava) compilaba como un método síncrono, así que las políticas solo protegían la construcción del pipeline y un fallo nunca se reintentaba ni tenía timeout. Ahora es [R4C-ASY-002](errors.md#r4c-asy-002); devuelve un `CompletionStage` en su lugar (`uni.subscribeAsCompletionStage()`, `mono.toFuture()`).
- **Quarkus: dos casos que perdían la protección sin aviso son errores de build.** Un recurso de Quarkus REST que es una clase anotada ([R4C-QK-007](errors.md#r4c-qk-007): Quarkus REST crea las clases de recursos por su cuenta, así que la subclase generada nunca atendía los endpoints), y un bean protegido con `@LookupIfProperty`/`@LookupUnlessProperty` ([R4C-QK-006](errors.md#r4c-qk-006): la condición se ignoraba).

### Corregido

- **Quarkus: condiciones de build en clases anotadas.** `@IfBuildProfile`, `@UnlessBuildProfile`, `@IfBuildProperty` y `@UnlessBuildProperty` en una clase anotada se ignoraban, así que tanto la implementación de producción como la de pruebas eran beans (una inyección ambigua). Ahora la subclase generada de una clase deshabilitada también queda deshabilitada.
- **Anotaciones repetidas en las subclases generadas.** Los overrides ya no repiten las anotaciones de Bean Validation (`@Valid` y las restricciones, que Bean Validation hereda del método sobrescrito): un valor de retorno con `@Valid` impedía arrancar una aplicación Quarkus (HV000131). En Quarkus, un `@Named` de clase sin valor ahora nombra al bean como la clase anotada, no `…$Resilient`, y un método `@Scheduled` ya no le da dos scopes al bean. En Micronaut, una clase marcada con `@ResilientBean` que además tenía anotaciones de políticas propias aplicaba dos veces las políticas de su interfaz (un `@Retry(maxAttempts = 3)` hacía 9 intentos); su subclase generada ya no se vuelve a envolver.
- **Micronaut: subclases y `@MockBean` de clases anotadas.** La subclase generada llevaba `@Replaces(C.class)`, que Micronaut aplica a todo bean asignable a `C`: una subclase anotada de `C` (con su propio `@Named`) desaparecía, y el `@MockBean` de `C` en un test no dejaba ningún bean. La subclase generada ya no lo lleva; la integración deja fuera solo la definición de bean de la propia `C`, y un `@Inject C` sin calificador sigue prefiriendo `C$Resilient` sobre los beans de subclases, como Micronaut prefiere el tipo exacto. El stub de un `@MockBean` de una clase anotada ya no se reporta como desprotegido (R4C-MN-004). Una subclase generada compilada sin `-Ar4c.inject=micronaut` que Micronaut crea igualmente (su constructor repite `@Inject`) se reporta con R4C-MN-004, porque no tiene el ámbito de la clase.
- **Spring Boot.** El endpoint de actuator no arrancaba en aplicaciones web (`Failed to extract parameter names`), porque el módulo se compilaba sin `-parameters`. Una clase anotada con un constructor sin parámetros y otros, ninguno `@Autowired`, no arrancaba (`No default constructor found`): ahora Spring usa el espejo generado del constructor sin parámetros, como usa ese constructor en la clase. Los beans de una interfaz anotada genérica (`NameLookup implements Lookup<String>`) vuelven a poder inyectarse por su argumento de tipo (`@Autowired Lookup<String>`) una vez envueltos.
- **Dobles de prueba de beans protegidos.** Spring: un `@MockitoSpyBean` de una interfaz anotada se envolvía después de que Spring lo creara, así que `verify(spy)` fallaba con `NotAMockException`; los spies ya no se envuelven, igual que los mocks de `@MockitoBean`. Quarkus: `@InjectMock` sobre una interfaz anotada fallaba porque su envoltorio era `@Singleton`; ahora el envoltorio de un bean `@ApplicationScoped` también es `@ApplicationScoped` (detrás de un proxy de cliente). Micronaut: un `@MockBean` de una interfaz `@ResilientBean` (un `@Client`) hacía fallar el arranque con R4C-MN-003; ahora se inyecta tal cual.
- **Configuración y mensajes.** `down-when-open` (Spring, Micronaut y Quarkus) partía en su coma un id derivado como `com.acme.Charges#charge(java.lang.String,int)`, así que no correspondía a ningún breaker; ahora las partes se vuelven a unir. Micronaut con singletons anticipados hacía fallar el arranque con R4C-CFG-013 por una clave de instancia de un bean protegido `@Prototype`, `@Refreshable` o de ámbito de petición; el valor por defecto sigue siendo `warn` cuando existen esos beans. Un valor inválido de `resilience4cata.micronaut.verify-instances` ahora falla con el código nuevo [R4C-MN-006](errors.md#r4c-mn-006). El informe de arranque de Spring para R4C-CFG-013 indica `resilience4cata.spring.verify-instances=warn` para beans creados después del arranque (`@Lazy`, prototypes, pipelines). El mensaje de R4C-CFG-013 cierra la frase antes de las instancias conocidas y dice `<interface or class>`. Los enlaces de los mensajes y de los metadatos usan las URLs actuales del sitio.
- **Quarkus: interfaces anotadas genéricas.** `@Inject Store<String>` de un `Store<T>` anotado recibía el bean sin proteger, porque los tipos del bean wrapper eran raw; ahora conservan los argumentos de tipo del bean.
- **Las clases anotadas conservan los nombres de sus parámetros.** Los overrides de una subclase generada llamaban a sus parámetros `p0`, `p1`, …, así que fallaban en las clases anotadas las funciones que leen los nombres en el método invocado: `@Cacheable(key = "#sku")` y `@EventListener(condition = "#event.urgent")` de Spring, `@PathVariable`/`@QueryValue` sin nombre explícito en controladores de Spring MVC y Micronaut, y Bean Validation, que reportaba cada violación dos veces (`p0` y el nombre real). Ahora conservan los nombres declarados; solo se renombra un parámetro llamado `java`, `dev`, como la primera parte del paquete de un fallback estático, o que empiece por `r4c$`. Un método heredado de un archivo de clase solo tiene sus nombres si esa clase se compiló con `-parameters`, como hacen los builds de Spring Boot, Micronaut y Quarkus. Los wrappers de interfaces no cambian.

## [0.8.0] - 2026-10-27 :id=0.8.0

### Agregado

- **`resilience4cata-all`: una sola dependencia para empezar.** Depende de `core`, `annotations` y `config` y no tiene código propio, así que un proyecto necesita dos líneas: `resilience4cata-all` y el procesador en el path de procesadores de anotaciones (ninguna dependencia puede llevar un procesador ahí). También es un módulo JPMS, `dev.resilience4cata.all`, que lee los tres de forma transitiva. Los módulos por separado y el BOM funcionan como antes; úsalos para dejar las anotaciones solo en compilación. Incluido en el BOM. Ver [La forma corta](start/installation.md#la-forma-corta).

## [0.7.0] - 2026-10-27 :id=0.7.0

### Añadido

- **`locked = true`** en `@Retry`, `@Hedge`, `@CircuitBreaker`, `@RateLimiter`, `@AdaptiveLimit`, `@Timeout` y `@Bulkhead` (y `Pipeline.Builder.locked()`): los valores que fija la anotación ganan sobre los overrides por instancia (`instances.<id>.*`, `retryInstance(...)` y similares); los atributos que deja sin fijar se pueden seguir sobrescribiendo. Un override ignorado se escribe en el log al crear la instancia, lo lista el nuevo `registry.lockedOverrides()` (`LockedOverride`), y `config.verifyInstances(registry)` lo reporta clave por clave con el nuevo código [R4C-CFG-014](errors.md#r4c-cfg-014), así que las integraciones de Spring, Micronaut y Quarkus lo reportan al arrancar. El código generado solo cambia en las anotaciones con `locked = true`. Ver [Bloquear una instancia](guides/configuration.md#bloquear-una-instancia).
- El build compara la API pública de cada módulo publicado con la última versión (`./gradlew apiCompatibility`, parte de `check`), con japicmp.

## [0.6.0] - 2026-10-26 :id=0.6.0

### Agregado

- **`@AdaptiveLimit`: límites de concurrencia adaptativos**, sync y async, en interfaces, clases anotadas y `Pipeline.adaptiveLimit(...)`. Como un bulkhead, limita las llamadas que corren al mismo tiempo, pero mueve el límite por sí mismo, entre `minLimit` y `maxLimit`, según la latencia de las llamadas: `GRADIENT2` (el valor por defecto) compara la latencia promedio de cada ventana con un promedio de largo plazo, `AIMD` crece de a uno y retrocede por `backoffRatio` después de un descarte; los dos siguen concurrency-limits de Netflix. Un fallo de `dropOn` (por defecto una `CallTimeoutException`, una `BulkheadFullException` o una `TimeoutException` de las políticas de adentro) cuenta como descarte; los demás fallos no son muestras. Un límite lleno rechaza enseguida con la nueva `LimitExceededException`. El límite se recalcula una vez por ventana (`window`, al menos `minWindowSamples` llamadas) en el hilo que termina una llamada después de que la ventana terminó: sin hilo de fondo, sin asignaciones en el camino de éxito. Está entre el rate limiter y el timeout: `Fallback → Retry | Hedge → CircuitBreaker → RateLimiter → AdaptiveLimit → Timeout → Bulkhead`. API nueva: `AdaptiveLimitConfig` (con el ajuste de los algoritmos: `smoothing`, `rttTolerance`, `longWindow`, `queueSize`, `backoffRatio`), `AdaptiveLimitHandle` desde `registry.adaptiveLimit(id)`, `AdaptiveLimitSnapshot` en `registry.snapshot().adaptiveLimits()`, `AdaptiveLimitEvent.Rejected` y `LimitChanged`, `adaptiveLimitDefaults`, `adaptiveLimit`, `adaptiveLimitOverlay` y `adaptiveLimitInstance` en el builder del registry, claves de configuración externa `*.adaptiveLimit.*`, y las métricas `r4c.adaptivelimit.limit`, `r4c.adaptivelimit.concurrent.calls`, `r4c.adaptivelimit.limit.changes` y `r4c.calls.rejected{kind=adaptivelimit}` en los dos módulos de métricas. Nuevo error del procesador [R4C-ATR-009](errors.md#r4c-atr-009). Consulta [Adaptive limit](policies/adaptive-limit.md).
- `@Hedge` deja de lanzar intentos cuando un adaptive limit rechaza uno, como con un breaker abierto o un bulkhead lleno.
- **Tarjeta en la Dev UI de Quarkus**: en modo dev, `/q/dev-ui` muestra cada instancia de política del registry (breakers, bulkheads, rate limiters, adaptive limits, retries y hedges con sus presupuestos, timeouts), actualizada cada dos segundos, y puede forzar la apertura de un circuit breaker, deshabilitarlo o reiniciarlo. Solo en modo dev: la tarjeta y su servicio JsonRPC no existen en builds de tests ni de producción. Ver [Quarkus, Dev UI](guides/quarkus.md#dev-ui).

### Corregido

- El endpoint `resilience4cata` del actuator de Spring Boot ahora incluye los hedges cuando reporta una sola instancia (`/actuator/resilience4cata/{instance}`).

## [0.5.0] - 2026-10-26 :id=0.5.0

### Agregado

- **`resilience4cata-micronaut`: integración con Micronaut 5** (Micronaut 5.2 o posterior, Java 25, sin AOP). ### Corregido

- Con un ticker manual (`ManualClock`), un retry asincrónico cuyo siguiente delay es cero (`delay = 0`, o un jitter `FULL` que sortea cero) lanzaba el siguiente intento en un hilo virtual nuevo en lugar de en el reloj, así que los tests competían con él. Ahora todo delay que una política programa en un ticker pasa por `Ticker.schedule`, también el cero, y se ejecuta en el hilo que avanza el reloj la próxima vez (también con `advance(Duration.ZERO)`), como ya hacían los hedges tras una falla. Sin ticker no cambia nada. `Ticker.schedule` puede recibir ahora un delay de cero.
- [R4C-RT-003](errors.md#r4c-rt-003) en una imagen nativa de GraalVM ahora también señala los metadatos de alcanzabilidad que escribe el procesador (`META-INF/native-image/dev.resilience4cata.generated/<clase>/reachability-metadata.json`), que deben estar en el class path del build de la imagen. En la JVM el mensaje no cambia.

### Cambiado

- `ResilienceEvent` admite un nuevo subtipo sellado, `HedgeEvent`: un `switch` sobre `ResilienceEvent` sin rama `default` deja de compilar hasta que maneje `HedgeEvent` (o añada `default`). `ResilienceSnapshot` tiene un componente nuevo, `hedges()`; su constructor de cinco listas se conserva. A partir de ahora la jerarquía crece en versiones menores: mantén una rama `default`, o escucha tipos de record específicos ([Observabilidad](guides/observability.md#listening)).
- La subclase generada para una clase anotada ya no es `final` (`public class C$Resilient extends C`), así que los frameworks pueden crear proxies de ella (CGLIB para `@Transactional`, proxies con scope). Los envoltorios de interfaces siguen siendo `final`.
- Los constructores generados de las clases anotadas nombran sus parámetros como el constructor de la clase (`registry, warehouse` en vez de `registry, p0`); un parámetro llamado `registry` hace que el del registry sea `r4c$registry`, y los parámetros llamados `java` o `dev` pasan a `r4c$p<índice>`. Las llamadas no cambian.

### Corregido

- **Cancelar una llamada async ahora cancela el trabajo que hay dentro.** Cancelar el future que devuelve un método async generado o `Pipeline.executeAsync` (o completarlo con una `CancellationException`) se detenía en la política más externa: el stage interno seguía corriendo, un slot del bulkhead quedaba ocupado hasta que ese stage terminara, un retry podía empezar otro intento, un fallback podía correr, y el circuit breaker podía registrar la cancelación como una falla. Ahora la cancelación baja por todas las capas hasta el stage del método: el retry cancela su backoff y no empieza más intentos, el timeout cancela su plazo, el bulkhead libera su slot en cuanto termina el stage (de inmediato para un `CompletableFuture`) y una llamada en cola sale de la cola, el breaker no registra nada (un permiso de half-open se devuelve), el fallback no corre, y una llamada que todavía espera un permiso del rate limiter lo devuelve y nunca empieza. Una cancelación no publica eventos. Un timeout que vence cancela las capas internas de la misma forma, así que un bulkhead dentro de un timeout libera su slot cuando la llamada vence. Cada política crea por llamada la misma cantidad de objetos que antes. Ver [Métodos async](guides/async.md#cancelación).

## [0.2.0] - 2026-10-25 :id=0.2.0

Corrige tres errores de comportamiento de la 0.1.0; uno de los arreglos cambia un valor por defecto (ver Actualizar).

### Actualizar desde 0.1.0

- Mantén `core` y `processor` en la misma versión (importa el BOM). El código generado por el procesador 0.2.0 necesita el `core` 0.2.0; el código generado por la 0.1.0 sigue enlazando contra el `core` 0.2.0, que solo agrega API.
- `abortOn` ya no contiene `CallNotPermittedException` por defecto, porque ahora un circuit breaker abierto detiene los reintentos por sí solo. Quita `CallNotPermittedException` de tus propias listas `abortOn` si lo agregaste solo para eso; dejarlo no causa problemas.
- Una llamada rechazada por un breaker abierto ya no se puede reintentar con ninguna configuración, ni siquiera con un classifier.

### Cambiado

- **Un circuit breaker abierto siempre detiene los reintentos.** Una llamada rechazada con `CallNotPermittedException` nunca se reintenta, digan lo que digan `abortOn`, `retryOn` o un classifier, en el código generado (sincrónico y async) y en `Pipeline`. En 0.1.0 esto venía del `abortOn` por defecto, así que definir tu propio `abortOn` lo quitaba sin aviso y el retry seguía llamando a un breaker abierto. `RetryConfig.DEFAULTS.abortOn()` (y `defaults.retry.abortOn`) ahora está vacío; [Retry](policies/retry.md#atributos).

### Corregido

- `FallbackEvent.Applied` ya no se publica para una falla que ningún método hermano de fallback recibe (por ejemplo un `Error` cuando el único hermano recibe `Exception`): esa falla se relanza, y el evento ahora significa que un fallback realmente se ejecutó.
- Los mensajes de error R4C-ATR-001 y R4C-CFG-002 indican la gramática de duraciones una vez en lugar de dos, y R4C-CFG-007 cierra la oración antes de "Known configs".
- El descriptor de módulo del procesador declara también `AnnotationClaimer`, así que `-Xlint:processing` no avisa cuando el procesador corre desde el module path de procesadores junto a otros procesadores.
- Un classifier que lanza dentro de `@CircuitBreaker` (o del breaker de un `Pipeline`) ahora termina la llamada enseguida, sync y async: el retry que lo rodea ya no clasifica la excepción del classifier como la falla del método ni la reintenta (lo que podía abrir el breaker y mostrar `CallNotPermittedException` en su lugar). El breaker registra una falla, el retry publica `GaveUp(CLASSIFIER_FAILED)` una vez, y el fallback o quien llama recibe la excepción del classifier. Ver [Un classifier que lanza](guides/classifiers.md#un-classifier-que-lanza).

## [0.1.0] - 2026-10-25 :id=0.1.0

Primera versión. Artefactos en Maven Central bajo el groupId `dev.resilience4cata`: `resilience4cata-annotations`, `-core`, `-processor`, `-config`, `-testkit` y `-bom`. Requiere Java 21 o posterior; probado en Java 21 y 25.

### Agregado

- **Seis políticas como anotaciones**, aplicadas en un orden fijo (Fallback → Retry → CircuitBreaker → RateLimiter → Timeout → Bulkhead → método): [`@Retry`](policies/retry.md) (backoff fijo o exponencial, jitter, presupuesto de tiempo), [`@CircuitBreaker`](policies/circuit-breaker.md) (ventana por cantidad o por tiempo, llamadas lentas, sondeos en semiabierto), [`@RateLimiter`](policies/rate-limiter.md) (GCRA, espera opcional), [`@Timeout`](policies/timeout.md) (en el thread de quien llama, basado en interrupciones), [`@Bulkhead`](policies/bulkhead.md) (semáforo, espera opcional) y [`@Fallback`](policies/fallback.md) (método hermano o clase handler).

- **`ResilienceRegistry`**: valores predeterminados, configs con nombre, sobrescrituras por instancia, instancias compartidas por `name`, handles para circuit breakers (`forceOpen`, `disable`, `reset`), rate limiters y bulkheads.
- **[Eventos y snapshots](guides/observability.md)**: listeners registrados en el builder del registry, snapshots de solo lectura de cada instancia.
- **`resilience4cata-config`**: [configuración externa](guides/configuration.md) desde archivos properties, recursos del classpath, variables de entorno y propiedades del sistema, con perfiles, `extends`, sobrescrituras por instancia, validación estricta y `verifyInstances` ([claves](reference/configuration.md)).

### Limitaciones conocidas

- No hay módulos de integración con Spring, CDI, Micrometer ni OpenTelemetry; no hay configuración en YAML.

- En el estilo de interfaz, las llamadas que una implementación se hace a sí misma no se interceptan.
- Solo se admiten `CompletionStage<T>` y `CompletableFuture<T>` como tipos async (no `? super T`, no tipos reactivos).
