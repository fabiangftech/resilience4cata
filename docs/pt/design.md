# Decisões de design

> **Status: a 0.13.0 está publicada no Maven Central.** As seis policies do MVP funcionam de ponta a ponta, síncronas e assíncronas, em interfaces e classes anotadas, além de configuração externa, classificadores, a API programática, eventos, snapshots e o testkit; veja o [status da implementação](#implementation-status). Chegou agora? Comece pelo [quickstart](start/quickstart.md). Esta página também resume as decisões de design tomadas antes do primeiro código (fase 1).
>
> Versão em espanhol: [es/design.md](../es/design.md)

resilience4cata é uma biblioteca de resiliência para **Java 21+ puro**: circuit breaker, retry, timeout, bulkhead, rate limiter e fallback, declarados com **anotações** que funcionam **sem Spring, CDI nem AspectJ**, e construída para ter **menos overhead que o Resilience4j**.

## Por que mais uma biblioteca de resiliência :id=why-another-resilience-library

1. **Anotações sem framework.** As anotações do Resilience4j só fazem algo através de Spring AOP, AspectJ ou Micronaut. O modo standalone do SmallRye Fault Tolerance é apenas programático. Nenhuma biblioteca popular oferece resiliência declarativa em Java puro ([01 §1.3, §4.2](research/01-landscape.md)).
2. **Desempenho mensurável.** O Resilience4j aloca em toda chamada (272 B/op para um circuit breaker simples na sua própria suíte JMH), usa uma trava na sua sliding window padrão e compõe as policies por meio de lambdas compartilhados que o JIT não consegue fazer inline ([01 §1.7](research/01-landscape.md), [03 §0](research/03-performance-internals.md)). O Polly v8 (.NET) mostra que alocação quase zero é alcançável.
3. **Múltiplas configurações como recurso de primeira classe**: configurações nomeadas com herança, perfis, anotações compostas definidas pelo usuário como `@ExternalCall`, e sobrescritas externas sem recompilar ([04 §6](research/04-api-and-configuration.md)).

## Decisões tomadas na fase 1 :id=decisions-taken-in-phase-1

| Tema | Decisão | Detalhes |

| Frameworks | Por enquanto, só Java puro | — |
| Módulos | Nomes de uma palavra: `annotations`, `core`, `processor`, `config`, `testkit`, `micrometer`, `bom`, mais os internos `benchmark`, `stress`, `examples` | [arquitetura](architecture.md#modules) |
| Dependências do `core` | Nenhuma além de JSpecify (veja abaixo) | [arquitetura](architecture.md#modules) |
| Policies do MVP | `@CircuitBreaker`, `@Retry`, `@Timeout`, `@Bulkhead`, `@RateLimiter`, `@Fallback` | [recursos](policies/README.md) |
| Contrato de desempenho | 0 B/op nos caminhos de sucesso, sem travas nos hot paths, garantido por JMH na CI | [recursos](performance.md) |
| Documentação | Markdown puro em `docs/en` e `docs/es`, servido pelo Docsify. O inglês é a fonte da verdade | [arquitetura](architecture.md#documentation) |
| Módulo `annotations` | Separado do `core` | [arquitetura](architecture.md#modules) |
| Durações | Strings (`"250ms"`, `"2s"`, `"PT2S"`), validadas pelo processor | [recursos](policies/README.md) |
| Build das convenções do Gradle | Included build chamado `conventions` (mantém a regra de uma palavra) | [arquitetura](architecture.md#build-and-tooling) |
| Processor | **Obrigatório.** Sem alternativa por proxy em tempo de execução. Se a classe gerada estiver faltando, `Resilient.of` falha na inicialização com uma mensagem que diz como adicionar o processor. O código que não pode ser anotado usa a API programática do `core` | [arquitetura](architecture.md#annotation-mechanism) |
| Retenção das anotações | `CLASS`: as anotações não são carregadas em tempo de execução, então `annotations` pode ser uma dependência `compileOnly`. Passar para `RUNTIME` depois é uma mudança compatível se algum dia for adicionada uma alternativa por proxy | [arquitetura](architecture.md#annotation-mechanism) |
| Anotações na interface vs na implementação | Com `Resilient.of(interface, impl, registry)` só contam as anotações da interface. No estilo de subclasse (`Resilient.create(Impl.class, registry)`), em que uma classe entra ao declarar ela mesma pelo menos uma anotação, as anotações da classe **vencem**, atributo por atributo: interface < método da interface < classe < método da classe (um método que sobrescreve um método da superclasse vence sobre ele). Métodos que sobrescrevem os de `Object` só recebem as anotações escritas neles | [arquitetura](architecture.md#interface-vs-implementation-annotations) |
| Autoinvocação | **Interceptada** no estilo de subclasse: `this.other()` passa pela sobrescrita gerada, então suas policies se aplicam. Não é possível no estilo wrapper de interface, em que as chamadas dentro da implementação do usuário nunca chegam ao wrapper; isso está documentado, e quem precisa disso anota uma classe não final | [arquitetura](architecture.md#self-invocation) |
| Anotações de nulidade | JSpecify como dependência real (`api`) do `core`: a única exceção a "zero dependências". É um jar só de anotações, de poucos KB, e dá informação de nulidade a IDEs, Kotlin e NullAway | [arquitetura](architecture.md#modules) |
| Hot reload | **Nenhum.** A configuração é imutável depois que o registry é construído; mudá-la significa reiniciar a aplicação. Isso mantém todo valor de configuração em campos `final` no hot path | [recursos](guides/configuration.md) |
| Coordenadas | Domínio `resilience4cata.dev`: groupId Maven `dev.resilience4cata`, pacote raiz `dev.resilience4cata` | [arquitetura](architecture.md#modules) |

## Decisões de API para a 1.0 :id=api-decisions

Tomadas quando a API foi revisada antes do congelamento ([plano até a 1.0](plan-1.0.md), fase 1). Cada uma mantém a API atual de propósito; mudá-la depois da 1.0 exigiria uma nova versão major, a menos que a mudança seja aditiva.

| Tema | Decisão | Por quê |
|---|---|---|
| `@Timeout` não tem `name` | Mantido | Um timeout não tem estado que valha a pena compartilhar por nome; seu `value` é a duração. Adicionar `name` depois é aditivo |
| Parâmetros de lista dos builders (`retryOn(List<Class<? extends Throwable>>)`) | Mantido | `List.of(A.class, B.class)` escrito na chamada infere o tipo certo; só uma variável com tipo `List<Class<? extends Exception>>` é recusada. Ampliar para `Collection<…>` não compensava uma segunda forma para cada atributo de lista |
| Ordem dos argumentos: `Resilient.of(type, delegate, registry)`, `Resilient.create(type, registry, args…)`, `Pipeline.builder(registry, id)` | Mantido | `create` termina com os varargs do construtor, então o registry não pode vir por último; `of` e `create` começam ambos pelo tipo, e `Pipeline.builder` não tem tipo para começar |
| Enum da anotação `LimitAlgorithm` vs `AdaptiveLimitConfig.Algorithm` | Mantido | Os enums das anotações são tipos de nível superior, onde `Algorithm` sozinho seria vago; os enums de configuração são aninhados, onde o nome da configuração os qualifica. Renomear o enum de configuração também quebraria o código gerado pela 0.13.0, que o nomeia |
| Formas dos snapshots (os snapshots de retry, timeout e hedge embutem `config`; bulkhead, rate limiter e adaptive limit copiam alguns campos; o do circuit breaker não tem nenhum dos dois) | Mantido | Cada snapshot traz o que um operador lê ao lado das contagens ao vivo; componentes podem ser adicionados depois (mantendo o construtor antigo), então um campo que falta ainda pode chegar |
| As taxas de `CircuitBreakerSnapshot` são `-1` antes de a janela ter `minimumCalls` | Mantido | Documentado no record, e o JSON dos endpoints mostra o mesmo `-1`. Um acessor `hasRates()` pode ser adicionado depois |
| `Pipeline.Builder.retry(String)` ao lado de `retry(Consumer)` (e os mesmos pares para cada policy) | Mantido | `retry(null)` é ambíguo, mas null nunca é um argumento com sentido ali; `retry(String, Consumer)` aceita um consumer nulo |
| `LockedOverride.policy` é uma `String` | Mantido | É a chave de configuração da policy (`retry`, `circuitBreaker`, …), o mesmo texto que um usuário escreve nas properties |
| Dois enums chamados `ExhaustedResult` (`Pipeline.ExhaustedResult`, e o da anotação, que também tem `INHERIT`) | Mantido | Eles ficam em módulos diferentes e raramente são importados juntos; a anotação precisa de `INHERIT`, a pipeline não pode tê-lo |

## Status da implementação :id=implementation-status

| Peça | Status |
|---|---|
| `@Retry` | **Pronto de ponta a ponta**: anotação, validação e geração no processor, runtime `RetryPolicy`, registry com padrões e configurações nomeadas, anotações compostas, mesclagem em nível de tipo e de método |
| `@CircuitBreaker` | **Pronto de ponta a ponta**: janelas por contagem e por tempo, máquina de estados lock-free, sondas em meio aberto com `maxWaitInHalfOpen`, chamadas lentas, `recordOn`/`ignoreOn`, instâncias compartilhadas por `name`, aninhado dentro de `@Retry`, e `forceOpen`/`disable`/`reset` através de `registry.circuitBreaker(id)` |
| `@Timeout` | **Pronto de ponta a ponta** (assíncrono: veja *Métodos assíncronos*). Métodos síncronos: a chamada fica na thread de quem chama e uma thread watchdog compartilhada a interrompe quando ela se atrasa (resolução: `timeout / 16`, 1–50 ms, nunca cedo); a interrupção é sempre limpa depois. Aplicado por tentativa, dentro do circuit breaker |
| `@Bulkhead` | **Pronto de ponta a ponta**: limite no estilo semáforo com `maxConcurrent`; com `maxWait = "0"` um contador lock-free cujas rejeições só leem, senão um semáforo não justo com o mesmo contador para os slots livres, que estaciona as virtual threads em espera sem pinning; instâncias compartilhadas por `name`; camada mais interna, então um slot só fica ocupado enquanto o método executa e a espera por um conta para o `@Timeout`. Métodos assíncronos com `maxWait > 0` esperam sem bloquear: entram numa fila FIFO, recebem diretamente um slot liberado (a chamada começa numa nova virtual thread) e são rejeitados depois de `maxWait`; quem chama de forma síncrona e assíncrona compartilha os slots, com justiça aproximada entre eles |
| `@RateLimiter` | **Pronto de ponta a ponta**: `permits` por `period` com GCRA (generic cell rate algorithm) sobre um `long`: uma rajada de até `permits` depois de um período calmo, e então uma permissão a cada `period / permits`; sem thread em segundo plano, e uma rejeição só lê. Com `maxWait`, uma chamada reserva a próxima permissão e dorme até a hora dela; uma espera interrompida devolve a permissão. Instâncias compartilhadas por `name`, inspeção através de `registry.rateLimiter(id)`. Camada dentro do circuit breaker, então chamadas rejeitadas pelo breaker não usam permissão |
| `@Fallback` | **Pronto de ponta a ponta** (assíncrono: veja *Métodos assíncronos*), como a camada mais externa, então também vê as rejeições (`CallNotPermittedException`, `BulkheadFullException`, `RateLimitExceededException`, `CallTimeoutException`). Duas formas, ambas verificadas em tempo de compilação: uma classe handler tipada (`FallbackHandler<T>`, `T` atribuível ao tipo de retorno, construtor público sem argumentos, uma instância por método) que recebe um `FallbackContext` com a falha, o número de tentativas e os argumentos; ou métodos irmãos com os parâmetros originais mais um parâmetro de exceção opcional, vencendo o tipo de exceção mais específico. Com o wrapper de interface, os métodos irmãos devem ser métodos `default`, abstratos ou `static` da interface, porque a classe gerada não pode chamar métodos privados. `applyOn`/`skipOn` filtram as falhas (`skipOn` vence). Com `@Retry`, o fallback executa onde o laço de retry desiste, então conhece as tentativas sem alocar nada no caminho de sucesso. Uma exceção checked lançada por um handler é relançada se o método a declara; senão, é envolvida em `UndeclaredThrowableException`. Métodos genéricos são suportados: os métodos irmãos declaram os mesmos parâmetros de tipo (por posição, com os mesmos limites) e são chamados com argumentos de tipo explícitos; uma classe handler só funciona quando o tipo do resultado não depende dos parâmetros de tipo do método |
| `@Hedge` | **Pronto (só assíncrono)** na 0.4.0: a mesma chamada é iniciada de novo depois de `delay` sem resultado, ou imediatamente depois de uma falha em `hedgeOn`; o primeiro sucesso vence e as outras tentativas são canceladas através de todas as policies internas (um breaker não registra nada, um bulkhead libera o slot). Um `int` de progresso por chamada, alterado por compare-and-set, decide o resultado exatamente uma vez; atrasos no timer assíncrono lock-free (ou exatos num `ManualClock`); um hedge budget (ativado por padrão) limita a carga extra. Exclusivo com `@Retry` num mesmo método; métodos síncronos são um erro de compilação por enquanto ([recursos](policies/hedge.md)) |
| `@AdaptiveLimit` | **Pronto** na 0.6.0, síncrono e assíncrono: um bulkhead cujo limite se move sozinho, entre `minLimit` e `maxLimit`, a partir da latência das chamadas (Netflix concurrency-limits: `GRADIENT2`, o padrão, ou `AIMD`), recalculado uma vez por janela pela thread que conclui uma chamada depois do fim da janela; os descartes (`dropOn`: timeouts e bulkheads cheios por padrão) fazem o AIMD recuar; só fail-fast, ainda sem Vegas ([página](policies/adaptive-limit.md)) |
| Métodos assíncronos | **Pronto** para todas as policies: um método que retorna `CompletionStage<T>` ou `CompletableFuture<T>` recebe a pipeline assíncrona, decidida pelo tipo de retorno (sem anotação extra). Uma exceção lançada antes de o delegate retornar um stage, ou um stage `null`, conta como chamada com falha. Os retries são agendados, nunca dormidos: a primeira tentativa roda na thread de quem chama, as seguintes em novas virtual threads. O timeout falha o future com `CallTimeoutException` e cancela o stage atrasado (`Future.cancel`); ele roda num timer lock-free (caixas de entrada em faixas, uma via por duração, cancelamento por um CAS de estado) que nunca dispara cedo e dispara no máximo cerca de dois ticks atrasado (tick = menor timeout assíncrono / 16, 1–50 ms), e um stage que já está completo pula o timer. O bulkhead segura seu slot até o stage completar. O `maxWait` do rate limiter reserva a permissão e inicia a chamada quando chega a hora, sem bloquear. Os fallbacks podem retornar `T` ou um stage de `T`. Uma thread de timer daemon para a biblioteca; tudo o que ela dispara roda numa virtual thread. Stages com curinga (`CompletionStage<? extends X>`, `CompletableFuture<?>`) são suportados: as policies, os fallbacks e os classificadores trabalham com o limite superior `X`, e os fallbacks também podem retornar um `CompletionStage<? extends X>`. Limites: sem `? super X` nem tipos de stage personalizados; cancelar o future retornado não cancela o delegate |
| `classifier` em `@Retry` / `@CircuitBreaker` | **Pronto**, síncrono e assíncrono: um `Classifier<T>` decide para resultados e exceções (`SUCCESS`, `FAILURE`, `IGNORE`), verificado em tempo de compilação, uma instância por método. Ele substitui `retryOn`/`recordOn` (combiná-los é um erro de compilação); `abortOn`/`ignoreOn` continuam vencendo. Um resultado `FAILURE` é retentado e, quando as tentativas acabam, retornado como está (sem `@Fallback`), ou lançado como um `ResultRejectedException` que vai para o `@Fallback` com `onExhaustedResult = THROW`. Um classificador que lança exceção (o do retry ou o do breaker) encerra a chamada imediatamente, com um evento `GaveUp` (`CLASSIFIER_FAILED`). Métodos sem classificador geram o mesmo código de antes ([recursos](guides/classifiers.md)) |
| API programática (`Pipeline`) | **Pronto**: uma pipeline imutável construída a partir de um `ResilienceRegistry` para código que não pode ser anotado; as mesmas policies, ordem e semântica do código gerado, síncrona e assíncrona, com fallback e classificadores, `run(...)` para chamadas sem resultado, fallbacks assíncronos que retornam um stage, e `onExhaustedResult`; sem alocação no caminho de sucesso síncrono ([recursos](guides/pipeline.md)) |
| Eventos e snapshots | **Pronto**: eventos selados tipados (transições e rejeições do breaker, retries, timeouts, rejeições de bulkhead e rate limiter, fallbacks), registrados no builder do registry, sem custo quando ninguém escuta; `registry.snapshot()` e `snapshot()` nos handles retornam records somente leitura ([recursos](guides/observability.md)) |
| Suporte a testes (`testkit`) | **Pronto**: `ManualClock` conduz retries, breakers, rate limiters, timeouts síncronos e assíncronos, esperas síncronas e assíncronas de bulkhead e atrasos assíncronos através de `Builder.ticker(...)`; jitter com semente com `Builder.random(...)` ([recursos](guides/testing.md)) |
| Classes anotadas (estilo de subclasse) | **Pronto de ponta a ponta**, síncrono e assíncrono: uma classe não final que declara uma anotação de resiliência recebe uma `<Class>$Resilient extends <Class>` gerada, criada com `Resilient.create(Type.class, registry, constructorArgs...)` ou `new Type$Resilient(registry, ...)`. Só os métodos com policies são sobrescritos, cada um terminando com `super.method(...)`, então a autoinvocação (`this.other()`) é interceptada. As anotações das interfaces implementadas e das superclasses são mescladas, atributo por atributo: interface < método da interface < classe < método da classe. Classes final, sealed, abstract, internas e privadas, records, enums, e métodos final anotados em nível de método são erros de compilação. Uma classe que só implementa uma interface anotada não é processada: ela recebe as policies da interface através de `Resilient.of` ([recursos](guides/annotated-classes.md)) |
| Configuração externa (módulo `config`) | **Pronto (MVP)**: arquivos properties, recursos do classpath, variáveis de ambiente (`R4C_…`) e propriedades de sistema (`r4c.…`); padrões, configurações nomeadas, `extends`, perfis, sobrescritas por instância (`instances.<id>.*`, que vencem os valores das anotações); uma configuração nomeada definida tanto no código quanto externamente recebe os valores externos atributo por atributo; validação estrita que reporta todos os problemas de uma vez com sua origem e um "você quis dizer" ([recursos](guides/configuration.md)), e `verifyInstances(registry)` para ids de sobrescrita que não correspondem a nenhuma instância.; `locked = true` numa anotação protege seus valores das sobrescritas por instância ([travamento](guides/configuration.md#locking-an-instance)). Ainda não: YAML |
| Registro de processamento incremental do Gradle | **Pronto**: o processor está registrado como isolating (`META-INF/gradle/incremental.annotation.processors`); cada classe gerada tem a interface envolvida como único elemento de origem, então editar um arquivo não relacionado recompila só esse arquivo, e editar um bundle, handler ou superinterface reprocessa só as interfaces que o usam |
| Benchmarks JMH | Retry (um e quatro serviços), circuit breaker (janelas por contagem e por tempo), timeout, bulkhead e rate limiter (1 e 4 threads), métodos assíncronos, classificadores e a `Pipeline` programática, contra o Resilience4j; execuções completas base contra nova em paralelo na AWS com `infra/bench.sh` ([benchmarks](benchmarks.md)) |
| jcstress (módulo `stress`) | **Pronto**: 21 testes jcstress das policies lock-free (contador do bulkhead, rajada e devolução do rate limiter, transições e estado quiet do circuit breaker, protocolo de carimbo de timeout/watchdog, eventos de transição do breaker publicados exatamente uma vez), verificados por mutação (17 de 18 mutantes detectados; um CAS só com release no fim de chamada do timeout é protegido por um teste, mas não foi reproduzido neste Mac). Execute com `./gradlew :stress:jcstress -Pjcstress="-m quick"`; `./gradlew build` só os compila |
| Códigos de erro | **Pronto**: todo diagnóstico do processor (`R4C-APT/ATR/CMP/ASY/CLS/FB/SUB`), erro de wrapping em tempo de execução e de pipeline (`R4C-RT`), erro de registry e de configuração de policy (`R4C-REG`: valores inválidos, configurações nomeadas desconhecidas ou duplicadas, instâncias compartilhadas conflitantes, ids de instância desconhecidos, com "Did you mean …?") e problema de configuração (`R4C-CFG`) tem um código estável e uma seção na [referência de erros](errors.md), com um exemplo errado e a correção; o build compila os exemplos do processor |
| Publicação | Configuração do Maven Central pronta (`r4c.publish`, `bom`, `centralBundle`); da 0.1.0 à 0.13.0 publicadas (`release.yml`) — veja [Releasing](releasing.md) |
| Guia do usuário | **Pronto**: [primeiros passos](start/quickstart.md), cada snippet compilado e executado por `examples/.../GuideTest.java`; `README.md` na raiz para o GitHub |
| CI (GitHub Actions) | **Pronto**, no GitHub: `build` em JDK 21 e 25 a cada push e PR (`./gradlew build -PtestJdk=N`), `alloc-gate` a cada PR (`./gradlew :benchmark:allocationCheck`: 40 benchmarks contra seus orçamentos de B/op em `benchmark/allocation-budgets.properties`), `stress` (jcstress quick, em x86 e ARM) depois de cada push para main e todas as noites, `stress-default` (jcstress no modo padrão em x86 e ARM) semanalmente, `stress-mutants` (manual: enfraquece uma guarda por vez e verifica que o jcstress a detecta, em x86 e ARM), `fuzz` (os testes de modelo e o teste de fuzz do processor com novas sementes) todas as noites, `soak` (todas as policies sob carga por 2 horas, verificando que nada cresce: [teste de soak](benchmarks.md#soak-test)) semanalmente, `mutation` (testes de mutação PIT do `core` contra seus testes unitários, um relatório dos mutantes que nenhum teste detecta) semanalmente, `sonar` (SonarCloud com cobertura), `consumer` (os artefatos publicados instalados e usados por um projeto Gradle e um Maven, no class path e no module path, como um usuário faria) em PRs que mexem no build ou no processor, `actionlint` nos arquivos de workflow; `release` (manual, numa tag `v<version>`) executa o `build` inteiro primeiro; Dependabot para o version catalog e as actions, que são fixadas por SHA de commit |
