# 当对冲请求争用同一个服务时

当慢调用只是运气不好时，对冲请求（hedge）能削减长尾，但当每次尝试都在同一个队列里等待时，它可能让长尾变得糟糕得多：本文对一个共享服务模拟 `@Hedge`，负载从 30 % 到 95 %。

*2026 年 11 月 5 日 · 作者 [fabiangftech](https://github.com/fabiangftech)，resilience4cata 的作者*

*同一天更新：表格现在给出十个种子的中位数，而不再只是种子 1 的结果；而默认预算在 95 % 负载下其实是一种缓慢崩溃。*

## 问题 :id=the-question

候选版本发布后，一位读者问：当第二次调用与第一次争用同一个下游时，对冲请求在长尾延迟下表现如何。这是个好问题。当第一个请求很慢时，对冲会发送第二个请求。如果第一个请求慢是因为运气不好（一次 GC 停顿、一次冷缓存、一块慢磁盘），第二个请求通常会胜出，长尾随之缩短。如果第一个请求慢是因为服务很忙，第二个请求会让它对所有调用方都更忙。

[对冲请求页面](../policies/hedge.md)已经说过不要对已饱和的依赖使用对冲，并且对冲预算"限制损害，但不能消除损害"。本文为这句话给出数据。

## 模拟方式 :id=how-it-was-simulated

这个问题关乎队列，而不是策略本身的开销，所以这不是 JMH 基准测试。JMH 在闭环中测量代码的开销，在那里慢服务也会拖慢调用方，从而掩盖本文要讨论的崩溃。取而代之的是一个模拟：它通过 `Pipeline`，在 testkit 的 `ManualClock` 上，用库自己的 `HedgePolicy` 和 `AdaptiveLimitPolicy` 对一个模拟服务进行调用：

- **服务：** 16 个 worker，以及一个由所有调用的所有尝试共享的 FIFO 队列，因此对冲请求要排在其他调用方的第一次尝试之后。
- **服务时间：** 对数正态分布，中位数 10 ms；2 % 的请求改为耗时 100 到 300 ms。每个请求独立抽样，因此对冲请求通常不会碰上同一次卡顿。
- **到达：** 开环（泊松），到达速率在没有对冲时会让 worker 有 30 % 到 95 % 的时间处于忙碌状态。和真实用户一样，慢服务不会让到达变慢。
- **对冲：** 20 ms 后发起第二次尝试，略高于服务的 p95。
- **每个数据点：** 200,000 次调用，前 10 % 不计入测量，使用十个种子（1 到 10）。表格给出各种子的中位数，并在括号中给出 p99 的最低值和最高值（当它们不同时）。

对比的配置如下：

<!-- snippet: hedge-setups -->
```java
NO_HEDGE("no hedge", null),
HEDGE_NO_BUDGET("hedge, no budget", b -> b.hedge(h -> h.delay(DELAY).budgetPercent(0))),
HEDGE_DEFAULT_BUDGET("hedge, default budget", b -> b.hedge(h -> h.delay(DELAY))),
HEDGE_BUDGET_5("hedge, budget 5 %", b -> b.hedge(h -> h.delay(DELAY).budgetPercent(5))),
HEDGE_BUDGET_ADAPTIVE("hedge, default budget, adaptive limit", b -> b.hedge(h -> h.delay(DELAY)).adaptiveLimit()),
THREE_ATTEMPTS_NO_BUDGET("3 attempts, no budget", b -> b.hedge(h -> h.delay(DELAY).maxAttempts(3).budgetPercent(0)));
```

默认预算允许 10 % 的调用发起对冲，外加 10 秒内每秒 1 次。自适应限流使用默认值（Gradient2）。模拟唯一改变的是：被取消的尝试是否会停止它在服务器上的工作。

> [!NOTE]
> 这些是模型的结果，对给定种子是确定性的，而不是挂钟时间的测量。它们展示策略如何对负载做出反应；真实的网络、真实的定时器和真实的服务器会增加模型所忽略的噪声和开销。代码在 `examples/src/test/java/dev/resilience4cata/examples/hedgesim` 中，`./gradlew :examples:hedgeSimulation` 会写出完整报告。

## 当服务器忽略取消时 :id=when-the-server-ignores-the-cancellation

这是 HTTP 调用的常见情况：当一次尝试胜出时，对冲会取消另一次，但取消只是让客户端不再等待。服务器仍然会把工作做完。

p99 / p99.9 延迟（ms），按无对冲时的负载列出（十个种子的中位数；括号内为 p99 的最低值和最高值）：

| 配置 | 50 % | 70 % | 85 % | 95 % |
|---|---:|---:|---:|---:|
| 无对冲 | 200 / 290 | 201 / 290 | 205 / 294 | 237 / 349 |
| 对冲，无预算 | **30 / 36** (30–76) | 崩溃 | 崩溃 | 崩溃 |
| 对冲，默认预算（10 %） | **30 / 36** (30–33) | 373 / 460 (322–407) | 530 / 616 (421–610) | 缓慢崩溃 |
| 对冲，预算 5 % | **30 / 36** (30–31) | 154 / 275 (130–168) | 216 / 336 (191–262) | 962 / 1,049 (423–1,652) |
| 对冲，默认预算，自适应限流 | **30 / 36** (30–31) | **58 / 268** (56–63)，1.5 % 被拒绝 | **122 / 293** (102–157)，3.8 % 被拒绝 | **167 / 305** (149–182)，7.4 % 被拒绝 |
| 3 次尝试，无预算 | 10 个种子中有 4 个崩溃 | 崩溃 | 崩溃 | 崩溃 |

"崩溃"指队列永远排不空：每次调用都等待足够长的时间而发出对冲请求，于是负载翻倍（三次尝试时翻三倍）并保持在那里。之后延迟在整个运行期间持续增长，这里一直增长到几分钟。"缓慢崩溃"是同样的情况，只是额外负载更少：worker 99.9 % 的时间都在忙，队列缓慢增长。使用种子 1 时，100,000 次调用后 p99 为 2.6 s，200,000 次后为 6.7 s，400,000 次后为 14.2 s，因此没有任何单一数字能描述它。

这些数字说明：

- **在有余量时，对冲请求如承诺般有效。** 负载不超过 50 % 时，无论有无预算，p99.9 都从 290 ms 降到 36 ms，代价是多 2.3 % 的请求。没有预算时，十个种子中有一个因一阵突发到达把 p99.9 推到了 199 ms。
- **没有预算，它会崩溃。** 一旦排队让普通调用超过 20 ms 的延迟，它们也会发起对冲，额外的负载让队列一直很长。它不会自行恢复：这是一种稳定状态。三次尝试的配置在 50 % 负载时就在十个种子中的四个里崩溃了，每次都是在一阵突发到达之后。
- **预算能防止崩溃，但不能防止损害。** 请求数从不超过每次调用 1.10 次。但因为排队而不是因为卡顿而触发的对冲会耗尽预算，并在余量很小的地方增加负载。从 70 % 负载开始，使用默认预算时的长尾比完全不对冲还要差。在 95 % 时，多出的 10 % 负载放不进 5 % 的余量，服务缓慢崩溃。
- **更小的预算有帮助。** 这里 2.2 % 的调用需要对冲，5 % 对它们来说足够了。它在每种负载下都比 10 % 好，在 70 % 时胜过无对冲，但在 85 % 和 95 % 时仍然比无对冲差。在 95 % 时它让 worker 达到 99.5 % 的忙碌率，而它的 p99 在各种子间波动最大：从 423 到 1,652 ms。
- **自适应限流让长尾保持较短。** 随着延迟上升，它会降低允许同时进行的尝试数，并拒绝其余的尝试，第一次尝试和对冲请求一视同仁；一次被拒绝的对冲也会停止后续的对冲。它也是各种子间最稳定的配置。在 95 % 负载时，p99 为 167 ms，而无对冲时为 237 ms，但有 7.4 % 的调用被以 `AdaptiveLimitFullException` 拒绝，调用方必须处理它（例如使用降级）。

## 当取消能到达服务器时 :id=when-the-cancellation-reaches-the-server

当取消能到达服务器时（例如 gRPC 会传播取消），在队列中的失败者会离开队列，正在服务中的则会释放它的 worker。情况完全改变了：

| 配置 | 50 % | 70 % | 85 % | 95 % |
|---|---:|---:|---:|---:|
| 无对冲 | 200 / 290 | 201 / 290 | 205 / 294 | 237 / 349 |
| 上面任何一种对冲配置 | 30 / 36 | 30 / 36 | 30 / 36 | 31 / 38 |

在每种负载、每个种子下，每种对冲配置都给出相同的结果。取消慢的尝试节省了它剩余的工作：在 95 % 负载时，worker 有 74 % 而不是 95 % 的时间处于忙碌状态。在这里对冲反而减轻了服务的负载，因为大多数对冲提前结束了一个本会占用其 worker 100 到 300 ms 的请求。

## 结论 :id=what-to-take-from-it

- **弄清你的取消能否到达服务器。** 如果能，对冲在很宽的负载范围内都是安全的。如果不能，对冲需要余量。
- **保持预算开启。** 没有预算时，一阵突发就可能让服务进入一种无法脱离的状态。正因如此，resilience4cata 默认开启预算。
- **按你预期的对冲量设定预算。** 如果 2 % 的调用因运气不好而变慢，10 % 的预算就为排队引起的对冲留下了 8 %，而这些对冲只会增加负载。`budgetPercent` 就是这个旋钮。
- **在服务可能过热时，把自适应限流放在对冲之内。** 它把过载变成快速拒绝，而不是一条长队列。
- **把延迟设在仅由排队造成的延迟之上。** 接近中位数的延迟会在服务一忙起来时就对普通调用发起对冲。

## 注意事项 :id=caveats

- 一个服务，一个队列。真实服务有多个副本；发往较空闲副本的对冲可能比这里更有帮助，而负载均衡器把它发往同一个繁忙副本时则帮助更小。
- 卡顿是相互独立的。当所有副本共享同一条慢路径时（它们背后同一个慢数据库），对冲会等待两次且毫无帮助；模拟没有覆盖这种情况。
- 没有网络，没有真实定时器，没有线程调度。在真实时钟上、负载生成器和服务器位于不同机器上的验证，是未来可能的工作。
- 十个种子，一种服务时间模型，一个延迟值。曲线形状在每个种子中都成立，但 85 % 和 95 % 处的数字在种子间有差异，如括号所示（95 % 下 5 % 预算的情况最多相差四倍）。
- 模型中的取消是即时且无开销的。真实的取消需要一次网络往返，而许多服务器只在工作的步骤之间检查取消，所以第二张表是上限，而不是预测。

## 试一试 :id=try-it

一个种子大约一分钟跑完，表格中的十个种子大约十分钟：

```bash
./gradlew :examples:hedgeSimulation -Phedge.seed=1
./gradlew :examples:hedgeSimulation -Phedge.seeds=1-10
```

要在你自己的服务中尝试对冲，请从[对冲请求页面](../policies/hedge.md)和[自适应限流](../policies/adaptive-limit.md)开始。欢迎在[讨论区](https://github.com/fabiangftech/resilience4cata/discussions)提出问题并分享你自己服务中的结果。
